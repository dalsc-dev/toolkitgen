Understanding JWT Structure

JWT (JSON Web Token) is the standard for secure data transmission. Understanding its three-part structure is essential for debugging.

A JWT has three parts separated by dots:

  • Header - Algorithm and token type
  • Payload - Claims/data
  • Signature - Verification

Example Token Structure

XXXXX.XXXXX.XXXXX
 |     |     |
 |     |     +-- Signature
 |     +-- Payload
 +-- Header

JWT Header

The header specifies the algorithm:

Common Algorithms

  • HS256 - HMAC SHA-256 (symmetric)
  • HS384 - HMAC SHA-384
  • RS256 - RSA SHA-256 (asymmetric)
  • ES256 - ECDSA SHA-256
  • none - Unsigned (security risk!)

Header Example

{
  "alg": "HS256",
  "typ": "JWT"
}

JWT Payload

The payload contains claims:

Registered Claims

  • iss - Issuer
  • sub - Subject
  • aud - Audience
  • exp - Expiration time
  • nbf - Not before
  • iat - Issued at
  • jti - JWT ID

Custom Claims

Any custom data can be included:

{
  "userId": 123,
  "role": "admin",
  "permissions": ["read", "write"]
}

Signature Verification

Signatures verify token integrity:

HMAC (Symmetric)

Same secret for signing and verifying. Simple but share secret carefully.

RSA (Asymmetric)

Private key signs, public key verifies. More secure for distributed systems.

ECDSA

Elliptic curve approach - efficient and secure.

Common JWT Errors

Debugging common issues:

1. Token Expired

"Invalid token" - Check exp claim. Token may be expired.

2. Invalid Signature

Secret or key doesn't match. Verify key/cert correctness.

3. Malformed Token

Three parts required. Check for missing or extra dots.

4. Algorithm Mismatch

Signing and verifying use different algorithms.

5. Audience Mismatch

Token not intended for your application. Check aud claim.

Practical Debugging

Step-by-step debugging process:

1. Decode the Token

First step - decode without verification. Check decoded content is valid JSON.

2. Check Claims

Review expiration, issuer, audience claims.

3. Verify Signature

Confirm signature with correct key/secret.

4. Validate Business Logic

Beyond claims - verify user permissions, roles, etc.

JWT in Authentication

Common authentication flow:

  1. User logs in
  2. Server creates JWT with user info
  3. Client stores JWT
  4. Client sends JWT with requests
  5. Server verifies JWT on each request

Storage Considerations

  • HttpOnly Cookie - Most secure against XSS
  • Local Storage - Convenient but XSS vulnerable
  • Memory - Most secure but requires re-authentication

Security Best Practices

Follow these security measures:

  • Use short expiration times
  • Store secrets securely
  • Validate all claims
  • Use strong algorithms
  • Implement token refresh
  • Use HTTPS only

Token Expiration Planning

Choosing expiration times:

Short-Lived (15 min)

High security applications. Requires refresh token.

Medium (1 hour)

Balanced approach for most applications.

Long (24 hours+)

Less secure but better UX. Consider tradeoffs.

FAQ: JWT Debugging

1. What does "invalid signature" mean?

Token was signed with different secret/key. Can't trust the token.

2. How do I decode without verification?

Our tool decodes without verification - useful for debugging.

3. Can I change data in JWT?

Signature won't verify if data changes - must re-sign.

4. What's the "none" algorithm?

Unsigned tokens - never accept these in production!

5. How long is JWT valid?

Check exp claim. No built-in expiration.

6. Can JWT be decoded but not verified?

Yes - decoding doesn't verify. Only signature verification proves authenticity.

7. Is JWT encrypted?

No, encoded but not encrypted. Anyone can read payload.

8. How refresh tokens work?

Short-lived access token + long-lived refresh token. Refresh gets new access token.

9. Can JWT be revoked?

With stateless JWT, can't invalidate without blacklist. Consider server design.

10. What should I store in JWT?

Minimal user ID and role. Other data fetch from database.
