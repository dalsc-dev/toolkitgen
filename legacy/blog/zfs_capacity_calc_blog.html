What is ZFS and Why Should You Care?

ZFS (Zettabyte File System) is an advanced copy-on-write file system originally developed by Sun Microsystems (now Oracle) for enterprise-level data storage. It combines file system and volume manager capabilities into a single unified solution with remarkable data protection features.

Unlike traditional storage solutions, ZFS provides:

  • Integrated volume management: No need for separate LVM or hardware RAID controllers
  • Data integrity verification: Checksums detect and repair silent data corruption
  • Snapshots and clones: Point-in-time data backup and rapid recovery
  • Compression: On-the-fly data compression reduces storage requirements
  • Deduplication: Eliminates duplicate data blocks
  • RAID-Z configurations: Software RAID with better rebuild characteristics than hardware RAID

ZFS is the file system of choice for TrueNAS, FreeNAS, OpenZFS, and many enterprise storage solutions precisely because of these powerful features.

Understanding VDEVs: The Building Blocks of ZFS

Before diving into RAID calculations, you must understand vdevs—the fundamental building blocks of ZFS storage pools. A vdev is a collection of one or more disks that ZFS treats as a single device for redundancy purposes.

Important rule: Once you add a vdev to a pool, you cannot remove it without destroying the entire pool. This makes initial planning critical. Choose your vdev configuration carefully because it determines both your storage capacity AND your fault tolerance.

Types of vdev configurations include:

  • Stripe: Data written across multiple drives without redundancy—fastest but zero fault tolerance
  • Mirror: Data duplicated across 2+ drives—loses 50% capacity but survives all single-drive failures
  • RAIDZ1: Single parity—can survive one drive failure with approximately equivalent storage to striping with one drive's worth of parity
  • RAIDZ2: Double parity—can survive two simultaneous drive failures
  • RAIDZ3: Triple parity—can survive three simultaneous drive failures

RAIDZ1 Explained: Single Parity Protection

RAIDZ1 is the entry-level redundancy option for ZFS, providing protection against a single drive failure. It works similarly to traditional RAID 5 but with improved rebuild characteristics and no "write hole" vulnerability.

In a RAIDZ1 configuration with n disks:

  • Usable capacity = (n - 1) × smallest disk size
  • Parity = 1 disk equivalent
  • Minimum drives = 3

Example: Three 8TB drives in RAIDZ1 = 16TB usable capacity (loses one drive's worth to parity)

RAIDZ1 is ideal for non-critical data where you want protection but need maximum storage efficiency. However, during rebuild after a drive failure, the remaining drives experience increased stress, and a second drive failure during rebuild will destroy your data.

RAIDZ2 Explained: Dual Parity for Peace of Mind

RAIDZ2 provides dual parity, meaning your array can survive two simultaneous drive failures. This is the recommended configuration for most use cases, especially as drive capacities continue to increase and rebuild times lengthen.

In a RAIDZ2 configuration with n disks:

  • Usable capacity = (n - 2) × smallest disk size
  • Parity = 2 disks equivalent
  • Minimum drives = 4

Example: Six 8TB drives in RAIDZ2 = 32TB usable capacity (loses two drives' worth to parity)

RAIDZ2 is the sweet spot for homelab enthusiasts and small business storage. It provides excellent protection against drive failures while maintaining reasonable storage efficiency.

RAIDZ3 Explained: Maximum Protection for Critical Data

RAIDZ3 offers triple parity protection, capable of surviving up to three simultaneous drive failures. This level of redundancy is typically reserved for enterprise environments or situations where data loss would be catastrophic.

In a RAIDZ3 configuration with n disks:

  • Usable capacity = (n - 3) × smallest disk size
  • Parity = 3 disks equivalent
  • Minimum drives = 5

Example: Eight 8TB drives in RAIDZ3 = 40TB usable capacity (loses three drives' worth to parity)

While RAIDZ3 provides the most protection, the storage efficiency penalty makes it less practical for homelab use. Consider this configuration for archival systems, media libraries, or business-critical data.

Understanding RAIDZ Geometry and Stripe Width

One common source of confusion is how RAIDZ geometry affects usable capacity. In ZFS, RAIDZ configurations have a "width" that determines how many data disks are used before parity is calculated.

RAIDZ1 geometry examples:

  • 4 disks: 3 data + 1 parity = 3 data disks' worth of capacity
  • 5 disks: 4 data + 1 parity = 4 data disks' worth of capacity
  • 6 disks: 5 data + 1 parity = 5 data disks' worth of capacity

This means a 5-drive RAIDZ1 actually has better storage efficiency than a 4-drive configuration. Our RAID calculator handles all these calculations automatically for you.

Mirror Configuration: The Simple Approach

For maximum simplicity and performance, ZFS mirrors duplicate all data across paired drives. In a mirror vdev:

  • Usable capacity = 50% of total raw capacity
  • Any single drive can fail without data loss
  • Read performance improves significantly (ZFS reads from the fastest responding disk)
  • Write performance is comparable to a single disk

Example: Four 8TB drives as two mirrors = 16TB usable capacity (two pairs of 8TB mirrors)

Mirrors are excellent for boot drives, high-performance pools, or situations where you prioritize rebuild simplicity over storage efficiency.

Storage Math: Converting Binary vs Decimal Capacity

Another source of confusion is the difference between binary (base-2) and decimal (base-10) capacity measurements. Manufacturers label drives using decimal (1TB = 1,000,000,000,000 bytes), while operating systems often report binary capacity (1TiB = 1,099,511,627,776 bytes).

Practical example: An 8TB drive (decimal) shows as approximately 7.28TiB in your operating system.

Homelab Best Practices

Building a homelab storage solution? Keep these best practices in mind:

1. Match Drive Speeds

Always use identical drives (same model, capacity, firmware) within a vdev. Mixing drive speeds, sizes, or manufacturers can cause performance issues and unpredictable behavior.

2. Size Your Pool Correctly From the Start

While ZFS allows expanding pools by adding vdevs, you cannot remove them. Plan for future growth but don't overprovision immediately. Consider the 80% rule—ZFS performs best when pools are kept below 80% capacity.

3. Use ECC RAM

ZFS is memory-intensive and benefits significantly from Error-Correcting Code (ECC) RAM. While not strictly required, ECC reduces the risk of silent data corruption being written to disk.

4. Enable Compression

ZFS compression is essentially "free" performance—modern CPUs compress data faster than disks can write it, and the time saved usually exceeds the compression overhead. Use LZ4 (default) for most workloads.

5. Plan for Hot Spares

Configure hot spares that automatically replace failed drives in your pool. This reduces downtime and ensures continuous protection during the drive replacement process.

Understanding ZFS Resilvering and Rebuild Times

When a drive fails in a ZFS pool, the process of rebuilding data onto a replacement drive is called resilvering. The time required depends on pool size, drive speed, and system resources.

Modern high-capacity drives (14TB+) can take days to fully resilver, and the pool remains vulnerable to a second failure during this period. This is why RAIDZ2 or RAIDZ3 becomes increasingly important as drive capacities grow.

Factors affecting resilver time:

  • Total pool capacity and data written
  • Drive read/write speeds
  • CPU performance for parity calculations
  • System RAM (more memory = faster compression verification)
  • Workload on the pool during resilver

Frequently Asked Questions About ZFS Storage Capacity

1. How much storage do I lose with RAIDZ?

It depends on the configuration. RAIDZ1 loses the equivalent of one drive's capacity to parity. RAIDZ2 loses two drives' worth. RAIDZ3 loses three drives' worth. With larger vdev widths, the percentage loss decreases—for example, RAIDZ1 with 5 drives loses only 20% to parity.

2. What's the difference between RAIDZ and traditional RAID 5/6?

Unlike hardware RAID 5/6, RAIDZ is software-defined and offers: no write hole vulnerability, automatic healing on read, variable stripe sizes that eliminate RAID 5 write holes, and self-healing data integrity. RAIDZ also doesn't require a dedicated RAID controller.

3. Can I mix different sized drives in ZFS?

Yes, but ZFS uses the smallest drive as the baseline for calculations within a vdev. The extra capacity on larger drives is wasted within that vdev. A better strategy is creating separate vdevs of same-sized drives or using larger drives for new vdevs.

4. What happens if I lose two drives in RAIDZ1?

Two drive failures in RAIDZ1 typically result in total data loss for that vdev. This is why RAIDZ1 is not recommended for larger drive counts—use RAIDZ2 instead if you need single-parity efficiency with better protection.

5. How many drives should I use in a RAIDZ configuration?

For RAIDZ1: 3-6 drives is ideal. Larger configurations (7-10 drives) work but increase rebuild vulnerability. For RAIDZ2: 4-10 drives. For RAIDZ3: 5-16 drives. Many experts recommend keeping vdev widths between 4-8 drives for optimal performance.

6. Is ZFS mirror faster than RAIDZ?

Mirrors generally offer better sequential and random read performance because ZFS reads from the fastest responding disk. Write performance is similar. For mixed read/write workloads with redundancy, mirrors often win. For mostly sequential read workloads, RAIDZ can be comparable.

7. Can I add drives to an existing ZFS pool?

Yes, you can expand a pool by adding new vdevs. However, you cannot expand an existing vdev—once created, the vdev's geometry is fixed. The new vdev provides additional capacity but doesn't improve redundancy of existing data.

8. What's the minimum RAM for ZFS?

ZFS recommends 8GB minimum for basic use, 16GB for moderate workloads, and 32GB+ for deduplication or heavy compression. However, 1GB can work for learning purposes with a single vdev. More RAM = larger ARC cache = better performance.

9. Does ZFS deduplication require lots of RAM?

Yes. The deduplication table (DDT) requires approximately 4GB of RAM per 1TB of deduplicated data. For most users, deduplication is not recommended unless you have specific use cases (VM templates, duplicated files) and sufficient RAM.

10. How does ZFS handle sector errors and corruption?

ZFS uses end-to-end checksums for every block. When ZFS reads data, it verifies the checksum. If corruption is detected and you have redundancy (mirror or RAIDZ), ZFS automatically repairs the corrupted data from the redundant copy.

11. What is the ZFS ARC (Adaptive Replacement Cache)?

The ARC is ZFS's primary memory cache, storing frequently accessed data in RAM. A larger ARC dramatically improves read performance. The ARC only stores metadata by default, while L2ARC extends caching to fast SSDs.

12. Can ZFS work with SSDs for caching?

Yes. ZFS supports L2ARC (read cache on SSDs) and special vdevs (ZIL/intent log for write acceleration). These dramatically improve performance for workloads with random I/O patterns or write bursts.

13. What's a ZFS intent log (SLOG)?

The SLOG (separate log) stores synchronous write operations on a fast SSD before committing them to the main pool. This accelerates write-heavy workloads like NFS, databases, or virtualization.

14. How do I calculate usable capacity for multiple vdevs?

Multiple vdevs in a pool provide additional capacity and redundancy independently. Use our ZFS capacity calculator to determine storage for each vdev, then add them together for total pool capacity.

15. Is ZFS better than Btrfs?

Both are excellent file systems with different strengths. ZFS has a more mature feature set, better data integrity, and is battle-tested in enterprise environments. Btrfs is integrated into Linux and offers copy-on-write snapshots, checksums, and RAID capabilities but with some known stability issues in certain configurations.

16. Can ZFS run on Windows?

Not natively. ZFS is primarily a Unix/Linux/OpenZFS solution. However, ZFS on Windows (ZoL) can run in Windows Subsystem for Linux (WSL), and some commercial solutions exist. For Windows storage, consider alternatives like Storage Spaces or traditional hardware RAID.

17. How often should I scrub my ZFS pool?

Monthly scrubs are recommended for most pools, weekly for critical data. A scrub reads all data and verifies checksums, detecting and repairing any corruption. Schedule scrubs during low-usage periods as they are I/O intensive.

18. What is copy-on-write in ZFS?

ZFS uses copy-on-write (COW) semantics—when data is modified, new blocks are written rather than overwriting existing ones. This ensures the old data remains intact until the new data is fully committed, preventing corruption from interrupted writes.

19. Can I use ZFS for database storage?

Yes, ZFS works well for databases when properly configured. Use recordsize matching your database block size, disable atime and relatime, add a dedicated SLOG for write acceleration, and ensure adequate ARC size for your working set.

20. What's the difference between snapshot and clone in ZFS?

A snapshot is a read-only point-in-time copy that consumes no additional space initially. A clone is a writable snapshot that creates a new dataset from the snapshot, sharing blocks until either is modified.

21. How does ZFS handle compression?

ZFS compression (LZ4 default) compresses data on write and decompresses on read transparently. Compression typically provides 1.5-2x compression for text/documents, less for already-compressed media. The CPU overhead is negligible on modern processors.

22. Can ZFS replace my backup solution?

No single storage solution is immune to all failures. ZFS provides excellent data integrity and protection against drive failures, but you still need offsite backups for protection against fire, theft, or catastrophic failures. Use ZFS snapshots and replication for efficient local and remote backup strategies.

23. What is ZFS send/receive?

ZFS send creates a stream of all data and metadata for a snapshot. Receive recreates that snapshot on another ZFS system. This enables efficient incremental backups, replication, and disaster recovery across systems.
